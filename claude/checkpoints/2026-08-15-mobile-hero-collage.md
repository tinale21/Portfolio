## Follow-up: decouple headline visibility from layout distance

- Provided a screenshot marking the large blank gap between the collage and the headline text and asked to decrease it. Explained this gap was structural, not padding — the section needs to be at least one viewport tall for the headline to stay geometrically off-screen pre-scroll, and that requirement was already at its tightest possible value. Asked via `AskUserQuestion` which trade-off to accept (grow the collage / move it back up / relax the hidden-until-scroll rule); user's answer: "is there a way so that the typewriter moves up but is still hidden until the scroll" — i.e., decouple the two requirements instead of trading one for the other.
- Solution: stopped relying on pure layout position to hide the headline pre-scroll, and used opacity instead. Reduced the mobile-only block1 `min-height` from the full `calc(100vh-64px)` down to `calc(78vh-64px)` (a first-pass value, freely tunable now that correctness doesn't depend on it), which brings the headline's DOM position much closer to the collage — but added a `headlineOpacity` motion value (`useTransform(progress, [0, 0.05], [0, 1])`) on the headline's wrapper, so it's `opacity: 0` at `scrollY=0` regardless of where its box actually sits in the layout, then fades in over roughly the first ~40px of scroll.
- Also had to guard `headlineArrived` (the typewriter's start trigger) with `raw > 0` (i.e. "has actually scrolled at all") — previously it fired purely off the headline's geometric visibility, which used to coincide with real scrolling because the layout distance guaranteed it; with the layout distance now shorter, the geometric check could already be satisfied at `scrollY=0`, which would've silently started (and likely finished) the typing animation while still invisible.
- Caught a real mistake before shipping it: initially assumed applying `headlineOpacity` unconditionally would be a no-op on desktop (reasoning: desktop's block1 stays a full viewport tall, so opacity should already be 1 long before the headline is naturally reachable). Checked that assumption directly via Puppeteer instead of trusting it — it was wrong: the headline's *box* enters the viewport at a much shorter scroll distance than where the opacity range finishes ramping, so unconditional application added a real, visible fade-in to desktop's headline reveal that didn't exist before. Fixed by adding `isMobileViewport` state (via `matchMedia("(min-width: 1024px)")`, Tailwind's `lg`) and gating: `opacity: isMobileViewport ? headlineOpacity : 1` — desktop now renders a flat, static `opacity: 1` always, verified via the same Puppeteer scroll sweep to confirm it never dips below 1 at any scroll position.
- Tailwind gotcha avoided: the mobile/desktop min-height values (`min-h-[calc(78vh-64px)] lg:min-h-[calc(100vh-64px)]`) use a literal `64` rather than a `${NAV_HEIGHT}` template interpolation — Tailwind's arbitrary-value scanner needs static text in the source to generate the class; a JS-interpolated class name would silently fail to generate at build time. Documented the manual-sync requirement inline (same caveat NAV_HEIGHT's own original comment already flags for collage-layout.ts).
- Verified: `npx tsc --noEmit` clean; mobile `min-height` confirmed reduced (780px → 594.32px, matching `78vh-64px` exactly at an 844px viewport) with `opacity: 0` at `scrollY=0` despite the headline's box now sitting inside the initial viewport; opacity ramps smoothly with scroll (`0` → `0` at 10px → `0.83` at 100px); desktop `min-height` confirmed unchanged (`836px` = exactly `900-64`) with opacity flat at `1` across a full scroll sweep (0/30/60/100/400/836px); screenshots confirm the typewriter now appears (and types correctly, no glitches) after meaningfully less scrolling than before; desktop screenshot still pixel-identical; zero horizontal overflow; `NEXT_PUBLIC_BASE_PATH=/Portfolio npm run build` succeeds.
